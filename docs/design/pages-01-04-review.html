A read of Benchmarks, Results, Failure map and Data forge as they stand on v18. The short version: the benchmark run ledger is the best-designed object on the site, and it is the only place using its own type ramp. Everything else has drifted into ten box shells and seven caption styles. Below: what the ledger is actually doing right, a type scale that makes it legal everywhere, an inventory of what can be deleted, and two mocked directions.

01

The type scale

tokens.css · components.css

You are right that the ledger's sizes appear nowhere else — but the reason is not that the ledger is off-model. It is that the token scale stops at 13px and the ledger needed somewhere to put a headline, so it hardcoded four sizes locally. The scale is the thing that is wrong, not the ledger.

Every size currently shipping, and where it comes from
10px--t-microBR-00012 · ids, tallies, sub-cells
10.5px— none —Benchmark run ledger · used 5× as a caption size, no token
11px--t-labelField labels, notes, rail items — 43 uses, the workhorse
11.5px— none —button.compact
12px— none —.m-ledger-identity .sub · .m-run-context-tally b
12.5px--t-bodyBody copy, table cells, and (hardcoded) every button label
13px--t-dataInputs, h4, tally numbers
14px— none —Ledger secondary headline
16px— none —Ledger progress headline · analysis-handoff h3
17px--t-subDeclared in tokens.css. Zero uses anywhere in the app.
19px— none —recursive( ) wordmark
20px— none —Ledger benchmark name — the size you like
Six tokens are declared. Twelve sizes ship. Seven of them are hardcoded literals, and the one token nobody uses (--t-sub: 17px) sits right in the gap the ledger had to fill by hand.
Two half-steps that are noise, not steps

--t-body: 12.5px and --t-data: 13px are 0.5px apart, and a <button> at a hardcoded 12.5px sits next to an <input> at 13px in the same form row on page 01 and page 04. Nobody can see the difference; it just makes two tokens where there is one job. Same for 10.5px (five caption uses) against --t-label: 11px.

Proposed — six real steps, and the ledger becomes legal
10px--t-microBR-00012 · ids, kickers, sub-cells  (unchanged)
11px--t-labelLabels, captions, notes, compact buttons  (absorbs 10.5 and 11.5)
13px--t-bodyBody, table cells, inputs, buttons  (absorbs 12, 12.5; --t-data retires)
14px--t-leadObject title inside a row  (from the ledger)
16px--t-headThe one sentence that answers the page  (from the ledger)
20px--t-displaySubject identity  (from the ledger; replaces --t-sub)
Tracking rides along with the size, so it belongs in the token too: --track-lead: -.012em, --track-head: -.022em, --track-display: -.03em. Those three values are already in components.css — they just have no name.
Why the ledger reads better than the rest of the site

It is the only region with a three-level hierarchy inside one row: kicker (10px caps, status-coloured) → headline (16/20px, tight tracking) → detail (12px, muted). Everywhere else on 01–04 the hierarchy is two levels — 11px caption over 12.5px cells — so every region has the same weight and nothing announces what the page is for. Adding the top two steps to the scale is what lets pages 02–04 have a headline at all.

The shape it collapses to

One <Box> that takes title, optional lede, optional code, optional tally, and a collapsible flag — rendering shell + caption together. <TableBox> and <Cap> are used together every single time across all four pages, and <Panel> is already Cap with different padding. That is three components and roughly 120 lines of CSS becoming one.

Two component pairs that are the same component

exact structural twins

FailureAnalysisStatus  ≡  DataForgeStatus

Failures.tsx and DataForge.tsx each export a status component with the identical five branches — live/poll, failed, ready-and-refresh, ready, not-started — the identical .m-analysis-status class, and the identical HTMX attributes. Only the noun and the poll URL differ. One <JobStatus> component with {id, pollUrl, refreshUrl, nouns} replaces both.

14 columns, duplicated

Results RunRow  ≡  Failures SelectedRunSummary

The Tasks/Criteria grouped-header block — Total / Passed / Failed / Errored / Pass rate × 2 plus Status — is written out twice, once per file, with the same count()/rate() calls in the same order. Extract <RunMetricCells run /> and <RunMetricHead /> into views/ui/; page 03's version then becomes a one-liner — or disappears entirely under Direction A.

Three visual languages for one idea

"The control that advances the pipeline" is drawn three different ways: the sticky .m-handoff bar at the foot of every page, the big gradient .m-analysis-handoff card on 03, and the two .m-run-card tiles on 01 (one of which is permanently disabled — Recurse is not wired). A user learning the app has to learn "how do I go forward" three times. Pick one: a full-width action bar, placed where the work is, with the sticky .m-handoff reserved for navigation between stages and never for starting work.

03

Page notes

01 → 04

01 · Benchmarks

The answer is below the form

  • Order. The page opens with ~20 inputs (import, catalog, model, task picker, repeats, concurrency, then 13 more under Advanced) and the ledger — the thing you came to look at — is last. For a returning user the config panel defaults open. Invert it: ledger first, config as a collapsed drawer that auto-opens only when there is no run.
  • Run identity, three times. RunContext states BR-code + benchmark + model + criteria/tasks; the Cap tally states runs/tasks/checks; the ledger row states BR-code + benchmark + model + counts again. Within ~800px. The ledger row wins — drop the other two on this page.
  • Dead control. The Recurse card is disabled with a title explaining it isn't wired. It's half the visual weight of the action area. Hide it behind a flag until it does something.
  • The isOverall() flip. Math.floor(Date.now()/5000)%2 swaps the live row between "overall progress" and "active work" every 5s. Charming, but it means the number you're reading vanishes mid-read. Consider showing both — the row is 168px tall and has the space.
02 · Results

Good bones, no headline

  • It works. The grouped two-row header, the unlabelled pass-rate columns closing each group, ungraded as its own column, dash instead of zero — this is the most disciplined data design on the site. Don't touch the table.
  • No answer at the top. The page's job is "did this run pass", and you have to read an 12-column row to find out. This is exactly where --t-head earns its place: one 16px sentence above the table.
  • Criteria default to open. open={criterion.result !== 'pass'} means a bad run renders dozens of expanded reasoning blocks. Fine at 5 failures, unusable at 60. Consider open-by-default only under a threshold.
  • Filter discoverability. "Show failed only" appears only when notPassed > 0, tucked in the caption at the far right. It's the most useful control on the page.
03 · Failure map

A 14-column table with one row

  • The main offender. SelectedRunSummary renders the full grouped Tasks/Criteria table to display a single run. A one-row table is a description list wearing a table costume — and it forces a horizontal scrollbar to show facts RunContext already showed six lines above. This is the single best place to reuse the ledger row.
  • Colour cries wolf. .m-analysis-meta b paints the failed-criteria count --fail red. On this page failures are the input, not a fault — the expected reading is "good, we have signal". Red here trains people to ignore red.
  • Two handoffs stacked. .m-analysis-handoff ("next step · 03") sits above the sticky .m-handoff ("Send to Data forge · 04"). Two adjacent next-step affordances pointing at different steps.
  • Topic table is the payoff and it's third on the page, below the run summary and the handoff card. It should be second.
04 · Data forge

Five container shapes, one page

  • Shell count. .m-forge-card ×2 → .m-analysis-status → .m-tablebox ×2 → .m-document-queue + card grid → .m-split of .m-panel ×2 → .m-handoff. Eight regions, five shells.
  • Cards contradict the house rule. results.css argues, correctly, that "cards-on-a-wash made every verdict look like a separate object when the list is really one column of them" — and then the review queue is a 2-up card grid. Documents are a queue; make them a ledger list with the same .m-criterion disclosure the criteria use.
  • Two ledgers, one row each. "Data forge ledger" is a 7-column table showing one row. Same problem as page 03; same fix.
  • The bottom .m-split is read-only. Novelty threshold, auto-approve, and token usage are rendered as static <div class="m-input"> fakes styled to look like fields. Either make them fields or make them a tally line — a disabled-looking input invites a click that does nothing.
  • Hand-rolled caption. DocumentReviewQueue writes <div class="m-cap">…</div> literally instead of using <Cap>. One-line fix, keeps the component honest.
04

Direction A — "the ledger is the page"

promote what already works

Every stage gets a subject row in ledger typography at the top: identity at 20px, the one-sentence answer at 16px, a status kicker in the stage's colour, and a progress track. Supporting tables stay exactly as they are, underneath. The 14-column one-row tables on 03 and 04 are deleted outright. Below: page 03 rebuilt this way.

what this buys

Wins

  • The ledger ramp becomes the site's ramp. Your favourite object stops being an exception.
  • Deletes the one-row grouped tables on 03 and 04, and the horizontal scrollbar with them.
  • RunContext is redundant on any page carrying a subject row — one component removed from three pages.
  • Status colour finally has one job: the left stripe, the kicker, and the track all agree.
what it costs

Risks

  • A 168px subject row is a lot of vertical budget on a page whose real content is a long table. Consider a 96px variant for pages 02–04, keeping the tall one for the live run on 01.
  • The ledger row is grid-positioned with fixed columns (210px minmax(0,1fr)); making it reusable means parameterising the identity column.
  • Losing RunContext means losing "Switch run" — it has to move into the subject row's identity block.
05

Direction B — "instrument readout"

smaller change, same problem solved

Keep tables as the primary object everywhere. Instead of a tall subject row, each page opens with a single-line readout band: hairline-separated cells, 20px numerals in --t-display, a 10px mono kicker over each. It uses the same new type steps as Direction A but costs about 40 lines of CSS and no restructuring. Same page 03 for comparison.

what this buys

Wins

  • One component, <Readout>, drops onto all four pages unchanged — it's a list of {kicker, value, sub}.
  • Costs ~34px of height instead of ~168px, so the table stays above the fold.
  • Reads as an instrument panel, which is what the app's own CSS comments say it's aiming for.
  • Zero risk to the live-run ledger on 01 — that row stays exactly as it is, and now shares the scale.
what it costs

Risks

  • An eleventh box shell unless it explicitly replaces .m-run-context. Ship it as a replacement, not an addition.
  • Numbers without a bar are harder to feel. If a run's pass rate matters at a glance, the readout wants a hairline track under the band.
  • The subject name at 16px is less commanding than the ledger's 20px — page 02 and 03 lose a little "which run am I looking at" force.
Recommendation

Direction B first, Direction A on page 01 only. B gets the new type steps into every page for a day of work and deletes .m-run-context, the one-row tables, and the duplicate metric cells. Then, if the ledger row still feels like the better object once the scale is shared, promoting it on 02–04 is a small follow-on — the tokens are already there. Doing A everywhere first means restructuring four pages before knowing whether 168px of subject row is worth it on a page whose payload is a 60-row table.

Two things not to change
